# Database

## Production model
Firebase Realtime Database is initialized in `src/firebase.js`. The client reads public psychologist records and writes only authenticated user-owned profile/favorite/appointment data. `database.rules.json` is the source of truth for the checked-in rules; deploy and test it against the real Firebase project before launch.

## Schema
```text
psychologists/{psychologistId}
  id, name, avatar_url, experience, reviews, price_per_hour,
  rating, license, specialization, initial_consultation, about

users/{uid}
  name, email, createdAt
  favorites/{psychologistId}: true

appointments/{appointmentId}
  schemaVersion, userId, psychologistId, psychologistName,
  name, email, phone, date, time, comment, status, createdAt
```

Psychologist IDs are deterministic slugs generated by `scripts/seed.js`; this keeps seed runs idempotent and makes favorite references stable. Existing Firestore document IDs are not automatically compatible with these IDs. If the Firebase project already contains real user/favorite data, back it up and run an explicit migration before switching clients.

## Seed workflow
- `scripts/seed.js` reads `scripts/psychologists.json`, builds stable IDs, and replaces the `/psychologists` tree through the Realtime Database REST endpoint.
- The seed command requires `VITE_FIREBASE_DATABASE_URL` and the server-only `FIREBASE_DATABASE_TOKEN`; the token must remain in `.env` or the shell environment and must never be a `VITE_*` browser variable.
- Re-running the seed is safe for the same source file. It does not delete user or appointment data.

## Reads and pagination
- Psychologists use `orderByKey` or `orderByChild` (`name`, `price_per_hour`, `rating`) with a look-ahead record and `limitToFirst`/`limitToLast`.
- Every filter change and `Load more` click performs a new request. Descending filters reverse the returned server-ordered records after the query.
- Favorites are stored as a map so one child can be added/removed atomically; Realtime Database has no Firestore-style `where in` query, so Favorites hydrates IDs with individual reads.

## Appointment data
Appointment requests are stored under `/appointments/{appointmentId}` with an authenticated `userId`, psychologist snapshot, required contact/date/time/comment fields, `status: "pending"`, and a server timestamp. Rules permit the owner to create/read their request but do not permit browser edits or status changes. Retention and administrative processing still require a product/legal decision.
